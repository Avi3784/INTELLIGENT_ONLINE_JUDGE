# SYSTEM ARCHITECTURE DESIGN SPECIFICATION

**Project Name:** IntelliJudge  
**Document Target:** Core Infrastructure Blueprint (Monolithic MERN)  
**Version:** 1.1  

---

## 1. Executive Summary & Design Scope

The objective is to develop a comprehensive and user-friendly online judge platform using the
MERN (MongoDB, Express.js, React, Node.js) stack. It allows users to practice coding
problems, improve their algorithmic skills, and receive AI-driven feedback.

To accommodate a streamlined development cycle, this architecture utilizes a monolithic
Node.js backend. Rather than relying on complex asynchronous message brokers, each code
submission runs in a separate Docker container spawned directly by the main web server to
ensure isolation.

### Architectural Core Constraints

- **Hermetic Sandbox Isolation:** Untrusted code executes inside Docker containers with
  restricted privileges to prevent access to the host system.
- **Resource Limits:** The system sets strict CPU and memory limits for containers to
  prevent resource exhaustion, and enforces a maximum execution time to prevent infinite loops.
- **Simplified Trace State:** The execution engine captures variable states into a single
  JSON payload during the run, returning it via standard HTTP to the frontend for visual playback.

## 3. Core System Modules (Codebase Structure)

The project is strictly divided into two primary environments: `/frontend` and `/backend`. The
following modules define the actual application logic to be developed.

### 3.1 Client Tier (React SPA: /frontend)

- **Authentication Module:** Manages the Login and Sign-up interfaces and secure token
  storage in localStorage.
- **Dashboard Module:** Renders a catalog of available coding problems, categorized by
  difficulty constraints (Easy, Medium, Hard) with tag-based filtering.
- **Code Workspace Module (Primary UI):**
  - **Editor Component:** Integrates the Monaco Editor to provide syntax highlighting
    and autocomplete capabilities.
  - **Problem Description Component:** Displays the target problem, constraints, and
    sample inputs/outputs.
  - **Visual DSA Canvas Component:** Parses the JSON trace array returned from
    the backend and iterates through it on a timer, animating data structure changes
    step-by-step.
  - **AI Mentor Component:** A dedicated UI panel that displays the hints and
    complexity analysis generated by the Gemini API.

### 3.2 Monolithic Backend API (Express.js: /backend/server)

- **Auth Router:** Validates user credentials and issues secure JSON Web Tokens (JWT) for
  session management.
- **Problem Router:** Queries MongoDB to fetch problem statements and test case
  parameters. Supports full CRUD operations for admin users.
- **Submission Controller:** Acts as the primary traffic controller. Receives incoming code
  payloads, logs the initial "Pending" state in the database, and routes the payload to the
  Execution Engine.
- **AI Integration Module:** An isolated service file that constructs prompts, appending the
  user's code and execution verdict, and interfaces with the Gemini API to generate
  diagnostic feedback.

### 3.3 Execution Engine (Node.js Process: /backend/judge)

- **File Creator:** Extracts the user's code from the HTTP request and writes it to a
  temporary local file on the server.
- **Docker Spawner:** Utilizes the Node.js native `child_process.exec()` module to execute a
  shell command. It initiates a locked-down Docker container, mounts the temporary script,
  and executes it against hidden test cases.
- **Log Parser:** Reads the standard output (stdout) generated by the Docker container. It
  calculates the final verdict and extracts the variable trace data required for the frontend
  visualizer.

## 4. End-to-End System Execution Lifecycle

1. **Submission Entry:** The user writes code and submits. An HTTP POST request is sent
   to `/api/submissions/:problemId`.
2. **File Generation:** The Express backend creates a temporary file directly on the server's
   local file system.
3. **Docker Execution:** The server uses the native child process to run a Docker container
   with specific time and memory limits.
4. **Evaluation & Tracing:** Inside the container, the code executes. Output limits restrict the
   amount of output generated to avoid log flooding.
5. **AI Trigger:** After the container terminates, the backend sends the code and the final
   verdict to the Gemini API for a logic review and hint generation.
6. **Response Delivery:** The server packages the verdict, the AI feedback, and the visual
   trace array into a single JSON response and transmits it back to the React frontend.

## 5. Database Schema Design (MongoDB / Mongoose)

The database structure utilizes a denormalized document schema approach to optimize read
performance. All collections use Mongoose's built-in `timestamps` option which automatically
adds `createdAt` and `updatedAt` fields.

### 5.1 User Collection

| Field          | Type                  | Constraints                        |
|----------------|-----------------------|------------------------------------|
| _id            | ObjectId              | Auto-generated primary key         |
| username       | String                | Unique, Required, Indexed, Trimmed |
| email          | String                | Unique, Required, Lowercase        |
| passwordHash   | String                | Required (bcrypt, 10 rounds)       |
| isAdmin        | Boolean               | Default: false                     |
| solvedProblems | Array\<ObjectId\>     | References → Problem collection    |
| createdAt      | Date                  | Auto (timestamps)                  |
| updatedAt      | Date                  | Auto (timestamps)                  |

**Relationships:**
- `solvedProblems` → references `Problem._id` (tracks which problems a user has solved)
- Referenced by `Submission.userId`

### 5.2 Problem Collection

| Field            | Type                                            | Constraints                     |
|------------------|-------------------------------------------------|---------------------------------|
| _id              | ObjectId                                        | Auto-generated primary key      |
| title            | String                                          | Required                        |
| description      | String                                          | Required (Markdown supported)   |
| difficulty       | String                                          | Enum: "EASY", "MEDIUM", "HARD"  |
| tags             | Array\<String\>                                 | e.g., ["Arrays", "HashMap"]     |
| timeLimit        | Number                                          | Milliseconds, Default: 2000     |
| memoryLimit      | Number                                          | Megabytes, Default: 256         |
| sampleTestCases  | Array\<{ input: String, expectedOutput: String }\> | Visible to users             |
| hiddenTestCases  | Array\<{ input: String, expectedOutput: String }\> | Server-only, never sent to client |
| createdAt        | Date                                            | Auto (timestamps)               |
| updatedAt        | Date                                            | Auto (timestamps)               |

**Relationships:**
- Referenced by `Submission.problemId`
- Referenced by `User.solvedProblems`

### 5.3 Submission Collection

| Field          | Type       | Constraints                                       |
|----------------|------------|---------------------------------------------------|
| _id            | ObjectId   | Auto-generated primary key                        |
| userId         | ObjectId   | Required, Indexed → references User               |
| problemId      | ObjectId   | Required, Indexed → references Problem            |
| language       | String     | Enum: "python", "javascript", "cpp", "java"       |
| code           | String     | Required (the submitted source code)              |
| verdict        | String     | Enum: "PENDING", "AC", "WA", "TLE", "MLE", "RTE" |
| executionTime  | Number     | Milliseconds (measured inside container)          |
| memoryUsed     | Number     | Megabytes (measured inside container)             |
| aiFeedback     | String     | AI-generated feedback text (populated after eval) |
| traceData      | Object     | JSON trace array for visual playback              |
| createdAt      | Date       | Auto (timestamps)                                 |

**Relationships:**
- `userId` → references `User._id`
- `problemId` → references `Problem._id`

## 8. Non-Functional Requirements

### 8.1 Expected Concurrency

- **Target:** Support 50–100 concurrent users during portfolio demonstrations.
- **Code Execution:** Maximum 10 concurrent Docker containers. Submissions beyond this
  limit are queued with a "PENDING" status.
- **API Response Time:** All non-execution endpoints should respond within 200ms.

### 8.2 Monitoring & Logging

- **Application Logs:** All API requests logged with timestamp, method, path, status code,
  and response time using `console.log` structured output.
- **Error Tracking:** Global Express error handler catches unhandled errors, logs full stack
  trace, and returns sanitized error messages to clients.
- **Container Logs:** Docker execution stdout/stderr captured and stored with the submission
  record for debugging.
- **Future Enhancement:** Integrate with a logging service (e.g., LogDNA, Datadog) for
  production monitoring.

### 8.3 Backup Strategy

- **MongoDB Atlas:** Automatic daily backups enabled via Atlas (free tier includes basic
  backup). Point-in-time recovery available on paid tiers.
- **Code Repository:** All source code version-controlled in Git. Regular pushes to GitHub
  as the primary code backup.
- **No Local State:** The application is stateless (JWT-based auth, cloud DB). Any server
  can be replaced without data loss.

### 8.4 Fault Tolerance

- **Database Connection:** The server retries MongoDB connection on startup. If the
  connection drops mid-operation, Mongoose automatically reconnects.
- **Docker Failures:** If a container fails to start or crashes, the submission verdict is set
  to "RTE" (Runtime Error) with an appropriate error message.
- **API Failures:** All routes wrapped in try-catch blocks. Unhandled promise rejections
  caught by the global error handler.
- **Gemini API Failures:** If the AI service is unavailable, the submission still completes
  normally — AI feedback is marked as "unavailable" rather than failing the entire request.

### 8.5 Security

- **Password Storage:** bcrypt with 10 salt rounds. Raw passwords never stored or logged.
- **JWT Tokens:** 7-day expiry. Secret key minimum 32 characters in production.
- **Input Validation:** All user inputs validated and sanitized before database operations.
- **Docker Isolation:** Containers run with `--network=none`, `--read-only`, and memory/CPU
  limits to prevent host system access.
- **CORS:** Restricted to the known frontend origin in production.

## 9. AI Integration Module — Detailed Design

### 9.1 Overview

The AI module is one of the key differentiators of this platform. It uses the Google Gemini API
to provide intelligent, context-aware feedback on user submissions. The AI is triggered
**after** code execution completes, so it has access to both the code and the execution result.

### 9.2 Trigger Flow

```
User Submits Code
       │
       ▼
Code Executes in Docker Container
       │
       ▼
Verdict Determined (AC/WA/TLE/MLE/RTE)
       │
       ▼
AI Module Triggered (async, non-blocking)
       │
       ├── Constructs prompt with:
       │   ├── Problem description (title + constraints)
       │   ├── User's source code
       │   ├── Execution verdict
       │   ├── Test case results (pass/fail counts)
       │   └── Language-specific context
       │
       ▼
Gemini API Call
       │
       ▼
Parse AI Response → Store in Submission.aiFeedback
       │
       ▼
Return to Frontend
```

### 9.3 Prompt Construction

The AI module sends a structured prompt to Gemini with the following context:

```
SYSTEM: You are a coding mentor for an online judge platform. Analyze the 
submitted code and provide educational feedback.

CONTEXT:
- Problem: {title}
- Difficulty: {difficulty}
- Constraints: Time {timeLimit}ms, Memory {memoryLimit}MB
- Language: {language}
- Verdict: {verdict}

USER CODE:
{code}

INSTRUCTIONS:
1. If verdict is WA: Identify the logical error without giving the solution.
   Provide a hint pointing toward the correct approach.
2. If verdict is AC: Suggest optimizations and analyze time/space complexity.
3. If verdict is TLE: Explain why the approach is slow and suggest a more
   efficient algorithm class (e.g., "Consider using a hash map instead of
   nested loops").
4. If verdict is RTE: Identify common causes (null pointer, stack overflow,
   index out of bounds) based on the code.
5. Always include: Time complexity analysis, Space complexity analysis.
```

### 9.4 Latency Handling

- **Timeout:** The Gemini API call has a 10-second timeout. If exceeded, feedback is set
  to "AI feedback is currently unavailable. Please try again later."
- **Non-blocking:** The AI call runs after the verdict is determined. The response to the
  user includes the verdict immediately. If AI is still processing, the frontend can poll
  or the response includes whatever is available.
- **Caching:** For identical code+problem+verdict combinations, cached AI responses
  are returned to avoid redundant API calls.

### 9.5 API Failure Handling

| Failure Type          | Behavior                                           |
|-----------------------|----------------------------------------------------|
| Network timeout       | Return verdict without AI feedback, log error      |
| Rate limit (429)      | Retry once after 2 seconds, then return without AI |
| Invalid API key       | Log critical error, disable AI for the session     |
| Malformed response    | Return verdict without AI, log parsing error       |
| Service unavailable   | Graceful degradation — verdict still delivered     |

The core principle: **AI failure never blocks the submission verdict.** The judge works
perfectly fine without AI — the feedback is an enhancement, not a dependency.
